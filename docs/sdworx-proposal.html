Postura Knowledge

We treat SD Worx's knowledge the way Postura treats a security estate. We collect it read-only, map it as a graph, and check it continuously with deterministic rules. Every answer ships with a signed receipt that shows why it can be trusted.

Verdict

Keep the engine, drop the cyber use case

Postura answers "which parts of my environment fail which controls, and what is the evidence?" SD Worx's problem has the same shape: "which parts of our knowledge can I rely on for this client, and why?" The subject is different, so the compliance use case does not transfer. The mechanism does, and it is what makes our entry different from yet another RAG chatbot.

Does not fit

Reuse the cyber use case

Identity and cloud misconfiguration findings do nothing for a payroll consultant who is unsure which document to trust.

Recommended

Read-only collectors, a graph, YAML rules that decide, an LLM that only writes, and signed evidence. Point all of it at knowledge sources.

The problem we pick

One role, one moment of doubt

The brief asks us to pick one role and one workflow. We take the story SD Worx wrote themselves. A payroll consultant gets an urgent client question. Search turns up three documents and a Teams message. Each one is plausible and each has a different problem, so the consultant cannot act.

How Postura transfers

Same engine, new subject

Postura runs a six-stage pipeline. Four stages carry over almost unchanged. The data model is new, and the connectors and LLM step change shape. The one Postura rule we keep as-is is the one that matters most here: rules decide, the LLM only writes. In Postura the LLM never sets a control mapping. In Postura Knowledge it never decides whether a source is trustworthy. It drafts wording only from claims the rules have already cleared.

The core idea

Trust rules: deterministic, versioned, explainable

Each rule is a small YAML file with a Cypher query, written in the same format as Postura's controls/rules.yaml. A rule turns a vague feeling ("I'm not sure about this doc") into a named, visible reason ("no owner, last reviewed 2023"). Because rules are code, SD Worx can review them, change them and audit them.

# rules/trust.yaml, same shape as Postura's control rules
- id: claims-conflict
  severity: high
  observation_summary: "Two sources state different values for the same rule, country and period"
  remediation: "Ask the topic owner to confirm one value and record the reason."
  cypher: |
    MATCH (a:Claim)-[:ABOUT]->(t:Topic)<-[:ABOUT]-(b:Claim)
    WHERE a.country = b.country AND a.period = b.period
      AND a.value <> b.value AND a.id < b.id
    RETURN a.id AS id, b.id AS other, 'Claim' AS type
  affects: answers_citing   # Postura's "satisfies" becomes "affects"

Together the rules cover all four inspiration areas in the brief (Trust, Capture, Detect, Connect). When no cleared claim exists, the answer says so and points to the owner instead of guessing.

The trust path behind one answer

Postura lights up the chain from a weak identity to exposed data. Here the same traversal walks from an answer back to the people who stand behind it. It also shows the branch that was held back and which rule held it back.

The same graph also answers the reverse question. If BE policy v3 changes tomorrow, which answers, consultants and clients are affected? One query returns them, and their receipts show exactly which version they relied on.

Hackathon architecture

Lean build, with security designed in

Security is 10% of the score, and Aikido specifically checks IDOR and authorization. Postura never needed either, since it ran as a single admin user. So this is the one area that is new work, and we put it in the request path itself. Every query is limited to what the signed-in user may see before retrieval runs. Nothing the user may not see ever reaches the LLM prompt or the answer.

Decisions before we build

  1. Code reuse rule. Ask the organisers whether reusing earlier Postura code is allowed. If not, we port the patterns into a new repo. I recommend the new repo either way; it's cleaner for Aikido too.
  2. Persona and topic. My recommendation is a payroll consultant and a home-office allowance question across Belgium and the Netherlands. It mirrors the brief's own story.
  3. Name. "Postura Knowledge" ties the entry to your product. A neutral name also works if you'd rather keep Postura separate.
  4. Time and team. How many hours are left and how many builders we have decides whether the "Should" column fits.
